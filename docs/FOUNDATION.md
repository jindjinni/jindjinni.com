# Foundation v1 — the benchmark for this system

Set on 2026-10-06 by Radcliffe Green (Plantarz Property Solutions LLC). This is the baseline the platform is built on.
Everything we add or change from here is measured against it. It is tagged in git as `foundation-v1`.

To see exactly what the foundation was at any time: `git show foundation-v1`.
To compare today's code with it: `git diff foundation-v1`.
To go back to it if something breaks badly: `git checkout foundation-v1` (or branch from it).

## What the foundation includes

**Platform**
- Multi-tenant: every company has its own login and data. Every table is scoped by `organizationId`; all server code gets the company from `src/lib/tenant.ts` (`requireOrg`), never from the browser.
- Roles in one file, `src/lib/permissions.ts`: owner, admin, purchasing manager, purchasing agent, receiver, accountant, customer service, "Custom access" (and legacy staff). No scattered role checks.
- Sign-up with email verification, invitations, team management, Admin panel, company close/purge, data export, appearance (themes), terms acceptance, business profile.
- Hand-picked access per person (Settings > Team & access): a role is the starting point, and on top of it an admin can open any other department for one person, either "Can look" (view) or "Can work" (also add and edit); Customer Service and Marketing only offer "Can use". Stored as JSON in `memberships.dept_access` (copied from `team_invitations.dept_access` when an invitation is accepted) and read by `parseAccess`. `requireOrg()` returns `org.access` next to `org.role`, and every department check takes both: `canViewReceiving(org.role, org.access)`. It only ever ADDS: HR, the Admin panel and manager powers (price overrides, archive, settings tabs) stay with the role, and "Custom access" is a role that starts with no department at all, so an admin can build a person up one department at a time. Chat rooms, the top menu, department layouts, file/CSV routes and server actions all follow it. New permission functions must take `(role, access?)` the same way.
- Staff logins (Team & access > "Create a username & password"): for people with no email. The admin enters a name and a login name; the username is `<login>_<company-slug>` (for example `maria_usa-test-strips-center`), unique across the platform and already tied to its company, so signing in on the normal page lands in that company. The server generates a 12-character password (`src/lib/staff-login.ts`) that is shown once, then only its hash is kept. The account has an unreachable placeholder email (`@staff.invalid`), `users.managed_by_org_id` (only that company's admins can reset the password), and `must_change_password` (a banner asks them to choose their own; the Terms page appears on first sign-in). Sign-in accepts an email or a username. Eight wrong passwords in a row pause that account for 15 minutes (`src/lib/login-throttle.ts`; counters on the user row); an admin reset lifts the pause. Staff logins count toward the company's seat limit like any other member.
- Platform principle: every company brings its own accounts. Anything that carries a company's identity or costs money per use is connected by that company in Settings and used only for it; the platform's own keys serve only the platform's infrastructure and its own companies. Shippo is done (the pattern to copy). Still to bring in line: the company mailbox for customer emails and campaigns (connectable today; the fallback to the platform's sending address should go for other companies), text messages (no provider yet; build as a per-company connector), the AI features (photo reading of lot numbers, news summaries; currently one platform key), and payments when added.
- Shippo connector (Purchasing > Settings > Connectors; the old Settings > Shipping address redirects there, owner/admin only; `src/lib/shippo-connection.ts`, `src/app/actions/shipping.ts`): every company plugs in its OWN Shippo account by pasting its token. We check it with Shippo first, keep it encrypted in `shippo_connections` (same AES-GCM helper as the mailbox connector; only the last 4 characters are ever shown again, the token is never sent back to the browser), show Live/Test mode and which carriers (USPS/UPS) are switched on in their account, and turn on live tracking in THEIR Shippo account automatically. Labels are bought and billed in the company's own Shippo account and its packages are tracked there. `shippo.ts` takes an explicit key (`shippoClient(key)`); nothing reads a key from the environment except `resolveShippo(organizationId)`, which returns the company's own connection, or the platform's `SHIPPO_API_KEY` ONLY for the companies the platform runs itself (the two built-in slugs plus the optional `SHIPPO_PLATFORM_ORG_SLUGS` setting) when they have not connected their own. Any other company without a connection simply cannot buy labels, so no company can run up charges on the platform's Shippo account. If Shippo refuses a saved token the connection flips to "needs attention", labels pause with a clear message, and pasting a new token fixes it. Webhooks: each company's notification goes to `/api/shippo/webhook?org=<company>&token=<secret for that company>`, so a company's Shippo account can only update that company's packages (the old platform address still works for the platform's own companies). The nightly sweep follows each company through its own token and skips companies with none.
- **Connectors** (the home of every "bring your own account" plug-in; `src/lib/connectors.ts`, `src/components/connector-card.tsx`, `src/components/dept-connectors.tsx`). Two places, owner/admin only (tab hidden from everyone else, pages 404, actions re-check): (1) every department that depends on an outside account has **Settings > Connectors** in its sidebar (`connectors` item in `DEPARTMENT_MENUS`, ids filtered per role by `menuIdsFor`) listing what it needs with live state (`DEPT_CONNECTORS`: Purchasing = Shippo connector, hosted in full on `purchasing/connectors`; Receiving = company email + Claude; Customer Service and Sales = company email; Marketing = company email + text messages). (2) Company-wide ones live in the company **Settings > Connectors** (`settings/connectors`): the company mailbox (card moved here from Customer Service Email Settings; OAuth return paths now `/dashboard/settings/connectors`) and the company's own **Claude key** (`src/lib/ai-connection.ts`, `ai_connections` table, `src/app/actions/ai-connector.ts`): checked with Anthropic (`/v1/models`, free) before saving, stored encrypted, last-4 only, refusal at use marks it Needs attention; the platform `ANTHROPIC_API_KEY` is used only for the platform-run companies (same slug list as the platform Shippo account). Photo reading (`readLabelPhoto`) and the news AI (`aiCheck`/`aiMaker`) resolve the key per company; a company without one gets keyword-sorted news and no photo reading. Text messages show "Not available yet" (no provider built). Customer email still falls back to the platform's shared sender when no mailbox is connected (open decision: remove it). New connector = add to `CONNECTORS`/`DEPT_CONNECTORS`/`connectorStatuses`, build its card on its page.

Footers carry the proprietary notice (operator: Plantarz Property Solutions LLC). `TERMS_VERSION` was bumped (2026-10-07.2) so everyone re-accepts. Technical layers: `src/app/robots.ts` (AI crawlers disallowed site-wide, app/API disallowed for all), response headers in `next.config.ts` (SAMEORIGIN + frame-ancestors, nosniff, referrer/permissions policy with camera=(self) for scanning, HSTS, `X-Robots-Tag: noai, noimageai`, plus noindex on the app/API), no browser source maps, no X-Powered-By. robots.txt is only a request; the Terms and logging are the enforcement. Not legal advice: have a lawyer review the wording.
- **Industry news is a built-in courtesy (no company key).** `newsAiKey` in `industry-service.ts` uses the platform `ANTHROPIC_API_KEY` for every company (falling back to a company key only if the platform has none). Cost is bounded per brand: each headline verdict is stored once in `industry_ai_cache` and each unknown brand's owner once in `industry_maker_cache`, then reused by every company that buys that brand (these tables hold public brand/news facts only, nothing company-specific). A company's brands are the product categories it has set up in Purchasing. Label-photo reading remains per-company (Settings > Connectors > Claude).
- Photos in Receiving: the live camera (`camera-capture.tsx`) opens as a full-screen "visualizer" view (the live picture fills the whole screen and also asks the browser for true full screen; controls float over it; the space bar takes a photo; clicking the last photo shows it at full size), asks for a wide 16:9 picture zoomed all the way out (with a Wider/Closer slider when the camera has zoom, and a Shape choice of Wide or Standard 4:3), asks the camera for its biggest picture (up to 8K), uses the camera's own still-photo mode where the browser offers it, keeps focus and exposure on automatic (with a "Focus again" button), and offers a Picture size choice (highest / 4K / Full HD). Every saved photo may be at most 4 MB, so `src/lib/client-image.ts` (`fitImageToBytes`, used by `prepareUploadFile` for the camera and for chosen files) keeps the picture exactly as it is when it already fits, otherwise saves the largest size that fits 4 MB at high JPEG quality (an 8K photo ends up about 4K). Photos that are only read on the computer (group photo for lot and serial numbers, label photo) are never uploaded and keep the camera's full size. Browser test: `cam_e2e.js` with fake 4K and 8K cameras.
- Public website and legal pages (`src/app/page.tsx`, `src/components/landing/*`, `src/app/(legal)/*`, `src/lib/legal.ts`): the homepage presents jindjinni as premium enterprise software covering every department (Purchasing, Receiving, Accounts, Customer Service, Inventory, Sales, Marketing, HR, Company Chat), the Home command center, Receiving safeguards, team access and security, and says it is built for up to 100,000 staff members (a design goal, not a measured or guaranteed capacity: the Terms say so). When a department or feature is added, update the `departments`, `flow` and point lists at the top of `page.tsx` so the page stays true. The Terms of Service, Privacy Policy, Acceptable Use Policy and Security page were rewritten on 2026-10-07 for the full platform: warranty disclaimers, liability cap, indemnity, binding individual arbitration with class-action and jury waivers (Florida law), regulated-product / recall / AI-feature disclaimers, email-and-text sender responsibility, workplace and chat duties. Changing them in a way people should re-accept means bumping `TERMS_VERSION` in `src/lib/legal.ts` (done: everyone is asked to agree again at next sign-in). Keep the Security page true to what the system actually does (for example the signup email code is described as "when turned on" while it is on hold). These texts are drafted by us and should be reviewed by a lawyer before the first paying customer. Test: `land_e2e.js`.

- Home screen (`/dashboard`, `src/app/(dashboard)/dashboard/page.tsx`): everyone lands here after signing in; it belongs to no department (first link in the top menu). It opens with a welcome banner ("Welcome to {company}", greeting by the company's time zone, today's date) and two closed sections (`HomeSection`, summary chips first, detail on Open): **Industry news** (everyone) and **Company performance** (Owner and Admin only, `canViewCompanyPerformance`; the numbers are never fetched for other roles). Company performance (`performance-panel.tsx`, numbers from `getCompanyPulse` in `src/lib/home-stats.ts`, day rules in `src/lib/home-rules.ts`) shows Purchasing (quotations given and their value, confirmed, delivered; waiting for the customer, on the way, shipping trouble), Receiving (shipments received and their value, with a problem found, needing an adjusted quote; in progress, waiting for a decision) and Accounts (orders paid and amount; orders to be paid, overdue, due today, using the same rules as Accounts) for Today / This week (Monday on) / This month, in the company's own time zone. Industry news is the industry watch for the brands the company buys: a "Needs your attention" box (urgent recalls, safety notices, bankruptcies in the last 45 days), then one closed, expandable line per brand (urgent count first), with a search and filters (Urgent only, Recalls, Safety notices, Business, New products). Brands = Purchasing categories (active) that hold at least one active product (`watchedBrands`); `src/lib/industry-brands.ts` maps a brand to its maker and its headline words (add a line there to cover a new brand). The basis of the screen is news FROM THE MANUFACTURER of each brand and about the maker's own products for that brand (recalls, safety notices, new and upcoming products, supply, business changes). A brand whose name is also an everyday word (Contour, Freestyle, OneTouch) is `ambiguous`: its bare name is never a match on its own, only product and maker words are (so "Contour Airlines" never shows); stories that no longer fit are hidden at once and deleted on the next refresh. Stories from the maker's own website or a press-release wire are marked "From the maker", FDA records "Official FDA record". Sources, read daily by `src/lib/industry-service.ts` (two news searches per brand: the maker's own announcements, then coverage of its products): the FDA's official device-recall list (openFDA, free) and Google News headlines for each brand. Stories live in `industry_news` (kept 180 days, shown 90), refreshes in `industry_watch_runs`. **Jin, the built-in assistant** (genie-lamp button, bottom right of every signed-in page)
- A guide and a read-only analyst. It explains how to use the platform from `src/lib/jin-guide.ts` (built from the real menus, only the departments and Settings pages that person may open), and answers questions about the company's own data through read-only tools (`src/lib/jin-tools.ts`: overview, quotations, customers, receiving shipments, unpaid orders, stock, industry news). A tool exists for a person only if `canView*` for that department is true, and always runs for the signed-in person's own company (the id comes from the session, never from the question). Jin cannot change anything: for "do it for me" it gives exact steps and a link. A later phase can add write actions with a Confirm button.
- Key and limits (`src/lib/jin-service.ts`, `jin-rules.ts`): the company's own connected Claude key when it has one (billed to the company, 400 questions per person per day as an abuse guard); otherwise the platform's key for every company, 40 questions per person and 300 per company per day. Only counts are stored (`jin_usage`), never the questions or answers. Model: `JIN_MODEL` env, default Haiku. Needs `ANTHROPIC_API_KEY` in Vercel.
- Industry specialist: Jin is the platform's only AI, running on Claude, made a specialist by (1) exact rule-based checkers in `src/lib/industry-checks.ts` (NDC shapes and 10/11-digit forms, GTIN check digits, GS1/UDI barcode text with lot/serial/expiry, lot and serial layouts written in plain 9/A/X symbols) that Jin calls instead of guessing, and (2) a knowledge library: facts built in (`industry-knowledge-builtin.ts`) plus entries the platform owner records at Settings -> Jin library (`jin_knowledge`, platform-wide, never company data). Only LIVE entries reach Jin, and going live needs a source and a last-checked day. "House rules" entries are always put in Jin's instructions. Jin never says a product is genuine, safe or recall-free; every check result carries that disclaimer. Brand-specific lot/serial layouts are never built in: they are recorded by the owner, with source and date.

Only they see the library page and the feedback inbox (`jin_feedback`: saved only when someone presses Helpful / Not right; the owner can turn a correction into a DRAFT entry, never straight to live).

- Safety: tool results, news and notes are treated as data, not instructions; answers can link only to `/dashboard/...` pages (anything else is shown as plain text, `parseInline`); input is length-capped and history is cleaned. Terms/Privacy describe Jin; `TERMS_VERSION` bumped to 2026-10-07.3.

## Jin's reading voice

Reading answers aloud uses the browser's own voices (free, nothing leaves the device). `src/lib/jin-voice.ts` picks the most natural voice the device has (Apple Enhanced/Premium, Google, Microsoft Natural), skips novelty voices and other languages, reads one sentence at a time at a calm pace, and the widget lets the person pick another voice (remembered as `jin-voice`). Until the owner says otherwise, everyone who has not chosen a voice gets the house voice "Google UK English Female" (`HOUSE_VOICE_NAMES` in `jin-voice.ts`; Chrome/Edge have it, other browsers fall back to the best natural voice). Reading aloud is ON by default for everyone (a pleasant surprise that Jin talks back); turning it off is remembered as `jin-speak=0`. What is spoken is not the screen text: `spokenText()` drops emoji, check marks and arrows and says symbols the way a person would ("then", "and", "percent"), so Jin never names an emoji. A paid human-like voice (OpenAI/ElevenLabs text-to-speech) is a possible later switch; who pays for it (platform with daily limits, or each company's own connector) is not decided yet, so do not add one without that decision.

## Business verification and approval (who we let in)

We only work with real, registered businesses. Sign-up (and the safety-net onboarding page) now requires, on top of the Business Profile: EIN (format and IRS-prefix checked, stored `XX-XXXXXXX`, one per non-rejected company), state of registration, business structure, state file number, year formed, kind of business, a short description, and one proof document (PDF/PNG/JPG up to 4MB, checked by its real bytes). All of it is read and checked in `src/lib/business-verification.ts`; the form is `components/business-verification-fields.tsx`; the choices live in `business-verification-options.ts` (browser-safe).

- A new company is saved with `organizations.approval_status = "pending"` and its proof in `business_verifications` (one row per company; the proof is base64 like the logo). `null` means approved: every company that existed before approvals were introduced stays untouched.
- `requireOrg()` redirects, and `requireOrgApi()` refuses, anyone in a `pending`, `rejected`, `suspended` or `banned` company (`isHeldBack` in `tenant.ts`); they land on `/under-review`. A rejected company's owner sees the platform owner's note and can fix and resubmit (`actions/verification.ts`); a suspended company sees why (it broke the Terms and Conditions) and cannot resubmit; a banned company sees that the account is closed.
- The platform owner (`isPlatformAdmin`) runs the **Companies panel** at Settings -> Companies (`settings/companies`; the old `settings/approvals` address redirects). It lists every company (built for ~10,000: search by name, EIN, email or web address; filters All / Waiting / Active / Suspended / Turned down / Banned; 25 per page, waiting first then newest; counts on top), and each company opens to its owner and contact, location, EIN and file number, kind of business, proof link (`/api/approvals/[orgId]/proof`, platform owner only, never cached), team size, last sign-in and its decision history. The list code is `src/lib/company-admin.ts` (paged in the database; `proof_data` is never selected for a list).
- Statuses: `pending` (waiting), `approved`/empty (active), `rejected` (turned down; the owner may fix and resubmit), `suspended` (locked out for breaking the Terms and Conditions; data kept; reversible by Reinstate), `banned` (permanent; account closed; its EIN can never sign up again because `einInUse` counts every status except `rejected`; the owner can Lift ban). Allowed moves are fixed in `actions/approvals.ts` (`MOVES`): pending -> approve / turn down / ban; active -> suspend / ban; turned down -> approve / ban; suspended -> reinstate / ban; banned -> lift ban. Turn down, suspend and ban need a written reason; ban also needs a confirm tick. The action re-checks the platform owner on every call and never lets a company change its own status. Every decision (and every sign-up / resubmission) is written to `company_decisions` (no foreign keys, so history outlives the company).
- **State-records check** (`src/lib/state-registry.ts`): once the response for a sign-up, safety-net onboarding or resubmission is sent (`after()`), the file number is looked up in the state's own free open-data register and compared with the legal name, business type, year formed and standing. Only New York, Colorado, Pennsylvania, Oregon and Connecticut publish their registers this way (Socrata portals, read through their published API; nothing is scraped and no site block is bypassed); other states get a "look it up on the state's site" link and the owner checks by hand. The answer (`matched`, `check` = look closer, `not_found`, `not_checked`, `error`) is saved on `business_verifications.registry_*` and shown only to the platform owner in the Companies panel, with a "Check again" button (`recheckRegistryAction`). It informs the owner and never approves, refuses or locks anyone; a failed or slow lookup never blocks sign-up. A paid all-50-states service (Cobalt, Middesk and similar) can be plugged in behind `checkRegistry` later. Tests use `REGISTRY_TEST_BASE` (`registry_e2e.js` + `fake_registry.js`). Optional `SOCRATA_APP_TOKEN` raises the portals' rate limit.
- Signup copies the EIN and file number into the Business Profile's Tax ID / registration number. The Terms (Accounts section) say we may approve, refuse or suspend any workspace and that false details breach them.
- There is no automatic lookup against the IRS or a state registry (that needs a paid service); the platform owner compares the proof with what was typed. Emailing the owner about new sign-ups waits on our sending email being active.

## The standards we keep (the "style" of the system)

1. **Plain language for people.** Screens, messages and PDFs say what happened and what to do next. No internal terms.
2. **Automatic first, manual by permission.** The system works out the answer (price, reason, checks); a person may adjust it only when their role allows, and an adjustment is visible as such.
3. **The server decides.** Anything the screen shows early (live price, photo-read numbers) is re-checked and recalculated on the server before it is saved.
4. **Safety over speed in Receiving.** A suspicious number, a repeat, or a recall hit stops or flags the item. A clean result never claims to prove authenticity ("OK" is not proof), and the receiver confirms what the reader suggested.
5. **Documents populate where you are working.** Finished quotations and adjustments appear in the same screen, simple format, with the reason; no extra windows or steps.
6. **One place for each rule.** Permissions in `permissions.ts`, pricing in `purchasing-price.ts`, number lists in `receiving-number-list.ts`, scan checks in `receiving-scan-core.ts`. Change the rule there, not in screens.
7. **Every change leaves a trail.** Receiving and Purchasing actions write to the audit log; money is never silently altered; voids reverse instead of delete.
8. **Tested before shipping.** Logic suites for numbers, scans, recalls, stress, and test-lock; browser end-to-end checks for the screens we change; `tsc` and `eslint` clean before a commit.
9. **Small, named commits.** One feature per commit, with a plain-language message.
10. **Every department has the same sidebar, and the company can edit it.** Each department (Purchasing, Receiving, and every one we add: Accounts, Customer Service, Inventory, Sales, HR, Marketing) opens with a colored sidebar down the left showing the company name and that department's tabs, with Setup pages under their own heading. An Administrator or Master Admin can press "Edit menu" at the bottom of the sidebar to rename any tab (and the Setup heading) and move tabs up or down; it saves for the whole company and has a "put the original names and order back" button. It is one shared component, `src/components/department-sidebar.tsx`, driven by one list per department in `src/lib/sidebar-menu.ts` (`DEPARTMENT_MENUS`) and saved in `organizations.sidebar_menus`. **To add a department:** add its tabs to `DEPARTMENT_MENUS`, use `<DepartmentSidebar>` in its layout (copy `receiving/layout.tsx`), and add its color in `src/lib/theme.ts`. Renaming and ordering then work with no more code. Tab names only change the sidebar; page titles stay as built. Roles decide which tabs a person sees (see the Purchasing layout), never the saved menu.
11. **A clean look, always: group the data, closed until opened.** The direction for the whole platform: wherever a page holds a lot of data, group it under closed, expandable headings by what it naturally belongs to (brand, day, customer, status), with totals and any warning badge on the closed line; a search or filter opens them; summary first, detail on request. For Receiving specifically, brand is the grouping. Every Receiving record or database page (Daily Receiving, Received Items, the Lot & Serial Tracker, and any new one such as Inventory or the weekly trackers) is grouped under the product brand, one closed line per brand with its totals and any recall or "needs a look" badge, opening to the detail. A search or filter opens the groups. The grouping rule lives in `src/lib/receiving-brand.ts`.

## How to change the foundation

The foundation is a starting line, not a freeze. When we deliberately improve it, we tag the new state (`foundation-v2`, ...) and add a short note here saying what changed and why. Ordinary work does not need a new tag.

**Quotation Profile** (Purchasing → Settings → Quotation Profile, `purchasing/quotation-profile`; Purchasing managers and above; table `purchasing_quotation_profiles`, code in `src/app/actions/quotation-profile.ts`): the company name and logo printed at the top of quotations, set by Purchasing on its own and separate from the main Business Profile, because a company may buy under a different name or brand. Quotations never print an address. A blank name or no logo falls back to the Business Profile's (`resolveBusinessDocumentIdentity(orgName, profile, quotationProfile)`); "Show the logo on quotations" can switch the logo off. It feeds the on-screen receipt, the receipt PDF, saved receipt versions (frozen at the time) and the adjustment PDF. Changes go to the Purchasing audit log. **The group heading under each department's sidebar is now "Settings" (it was "Setup"); a company that renamed it keeps its own name.**

**Inventory Department** (`/dashboard/inventory`; everyone except Customer Service can look; Purchasing managers, Admin and the Owner change it; code in `src/lib/inventory-rules.ts` (pure), `src/lib/inventory-service.ts`, `src/app/actions/inventory.ts`, tables `inventory_movements` and `inventory_estimates`). **Live Stock** shows what is in stock now, by brand, then product, then LINES. A line is one product + one condition + one expiration group, so 50 Mint sensors with 7+ months are one line and the Dinged ones, or the short-dated ones, each have their own. Expiration groups are the company's own Month Ranges (Purchasing), worked out from the real expiration dates and recalculated every day, so stock moves down a group as it ages (a past date is "Expired", no date is "No expiration date"). Each line shows the quantity, cost value, estimated value range, the actual expiration span and its lots; the product page (`inventory/p/[key]`) lists every lot and the serial numbers Receiving scanned. **Where stock comes from:** (1) Receiving, read live from the accepted units in `receiving_intake_lines` (nothing is copied, so a correction in Receiving shows at once), with the same rule as Daily Receiving: recalled, counterfeit/pending-review, fully returned lines are not stock, and neither is anything received "Expired"; stock counts as soon as the package is submitted. Cost per unit = the quotation line total / quoted quantity (the adjusted amount when the quotation was adjusted). (2) **Manual Add**: one or more lines (brand then product, condition, quantity, expiration, lot, cost per unit, estimated lowest/highest price), used for opening stock or corrections at any time, with a reason; each add is a row in `inventory_movements` (who, when, why) and the estimate is saved. (3) **Sales** takes stock out through `deductStock` (inventory-service.ts): it picks the layers earliest-expiration first, writes a negative movement per layer (with the cost taken out too) and refuses, changing nothing, if there aren't enough. Sales calls it (as `deductStockMany`, all-or-nothing) when an invoice is sent, and `returnSale` puts the units back on the same layers when a sent invoice is voided. **Stock History** lists every receipt, manual add, sale and correction. **Estimated Prices** (Settings) sets the lowest and highest price per unit by product and condition; Live Stock multiplies them by quantity. Not built yet: per-serial deduction and low-stock alerts (Sales reserves stock for draft invoices, see below).

**Sales Department** (`/dashboard/sales`; purchasing roles and the Accountant can look, the Accountant read-only; people who can write Purchasing make quotations and invoices; the Company Profile is for Purchasing managers, Admin and the Owner; Receiving and Customer Service don't see it; code in `src/lib/sales-rules.ts` (pure), `sales-service.ts`, `sales-pdf.ts`, `sales-import.ts`, `src/app/actions/sales.ts`, PDF route `src/app/api/sales/documents/[id]/pdf`, tables `sales_profiles`, `sales_buyers`, `sales_price_sheets`, `sales_price_items`, `sales_documents`, `sales_document_lines`, `sales_payments`). **Quotations and Invoices** are made in one editor: pick a buyer (fills contact, email, addresses, terms), type a product and the current stock appears beside it (on hand, held by other drafts, available, the expiry groups and other conditions), and the buyer's price from its price sheet fills the unit price; asking for more than is available is flagged in red. A quotation never touches stock and is numbered Q-1001..., and "Make this an invoice" copies it. **A draft invoice reserves its units** (other drafts see them as held); **sending it (emailing the PDF) takes the units out of Inventory**, earliest expiry first, all or nothing, and if the email fails the units are put back and it stays a draft. Voiding a sent invoice returns the units; an invoice with payments can't be voided. Invoice numbers come from the Company Profile counter (skipping numbers already used). **Payments** (Sent, Partly paid, Paid; Past due is worked out from the due date, never saved) are recorded on the invoice and the list groups by status with totals and amount still owed. **Buyers** are added by hand or imported from a CSV/Excel (company, contact, email, addresses, terms; same-name rows are skipped, so importing twice changes nothing); each buyer's **price sheet** is uploaded as Excel/CSV, columns are guessed, product names are matched to the catalog (ambiguous ones are listed under "Needs a match" to fix by hand) and the original file is kept for download. **Price Comparison** shows, per product in stock and condition (default Mint), what each buyer pays, who pays the most and by how much, stock worth at the best prices, and how many products each buyer wins. **Company Profile** holds the name, address, email, phone, logo, default terms/notes, footer and the next invoice/quotation numbers; the PDF copies the Airtable invoice builder's layout. Not built yet: sales tax rules, per-serial invoices, and automatic past-due reminders.

**HR Department** (`/dashboard/hr`; Admin and the Owner only, everyone else gets a 404; code in `src/lib/hr-rules.ts` (pure), `src/lib/hr-service.ts`, `src/app/actions/hr.ts`, `src/components/clock-widget.tsx`, tables `hr_time_events` and `hr_activity`). **The time clock** is at the top of every screen for every signed-in person: Clock in, Start break / End break, Clock out. Each press is stamped by the server (never the browser) and only the allowed next button is shown; clocking out on a break ends the break first. Hours = clock-in to clock-out minus breaks; a shift counts for the day it started; a shift left open for 16 hours is a forgotten clock-out, shown in red with no made-up hours. Days are the company's own time zone (Accounts payment terms), including daylight-saving days. **Staff Today** lists everyone, grouped by role (closed lines with totals), with status (Working / On break / Clocked out / Not clocked in), first sign-in, clock in, breaks, clock out, hours and that role's work counts (purchasing: quotations created, orders sent (shipping labels), invoices sent; receiving: packages opened and received; customer service: emails sent), for a day, week or month with a date picker. **Activity Log** lists every time-stamped action under the person who did it. **Time Sheets** give hours per person per day. Nothing is stored twice: quotations created, packages opened/received, customer emails and sign-ins are read from the tables that already stamp who and when; only work nobody stamped (shipping labels, invoices/quotations sent, payments, manual stock adds) is written to `hr_activity` through `logActivity` (never throws). Counts and the log both come from the same feed (`activityFeed`), so they always agree. To count a new kind of action, call `logActivity` where it happens and add it to `FEED_GROUPS` / `METRIC_OF_KIND`. Not built yet: an Admin fix for a forgotten clock-out, pay rates and payroll export, and automatic idle detection.

**Marketing Department** (`/dashboard/marketing`; Admin, Owner and Purchasing Managers only, everyone else gets a 404; code in `src/lib/marketing-rules.ts` (pure), `src/lib/marketing-service.ts`, `src/lib/marketing-token.ts`, `src/app/actions/marketing.ts` and `marketing-public.ts`; tables `marketing_contacts`, `marketing_optouts`, `marketing_campaigns`, `marketing_messages`, `marketing_settings`). **Contacts** = every active Purchasing customer (read live, never copied) plus contacts typed in or uploaded (CSV/Excel; name, email, phone, company); an uploaded person whose email or phone is already a contact is skipped, and a customer wins over a duplicate contact. People are grouped (Customers from quotations, Uploaded and typed-in, Unsubscribed) in closed lines. **Email campaigns** are written with `{first_name}`, `{last_name}`, `{name}`, `{company}`, previewed with real names, test-sent to your own address (a test is never counted as a send), then sent after a confirmation. Audience: Everyone, Customers only, or Uploaded contacts only. The first send press fixes the recipient list (so a double click can't duplicate it); the browser then sends 25 at a time through `sendOrgEmail` (the company's connected mailbox, else the platform address) with a progress bar; 3 failures in a row pause it and Resume continues; Stop skips the rest. A mailing address (Email Settings) is required, there is a daily limit (default 500, max 2,000) counted over the last 24 hours, and every email ends with the sender, mailing address and a signed unsubscribe link (`/unsubscribe/<token>`, public, no sign-in, one press, safe to open twice). Unsubscribes and the Stop buttons on Contacts are checked again before every batch, so someone who unsubscribes mid-send is skipped. **Text campaigns** can be written, previewed (with the STOP line added and the text count) and saved as drafts, but sending is off until a text provider is connected (Text Settings holds the provider choice, from-number and opt-out line; nothing is sent today). Not built yet: a text provider, scheduled sends, open/click tracking, and a List-Unsubscribe header (the email connector has no custom-header support).

**Chat** (`/dashboard/chat`; every signed-in person in the company, every role; code in `src/lib/chat-rules.ts` (pure), `src/lib/chat-service.ts`, `src/lib/chat-emoji.ts`, `src/app/actions/chat.ts`, API routes under `src/app/api/chat/`, the screen in `dashboard/chat/`, and the "Chat" link with its red unread count in `(dashboard)/chat-nav-link.tsx`; tables `chat_messages`, `chat_attachments`, `chat_reads`, `chat_presence`). The company's own mini messaging app. **Rooms** are never stored, they are worked out: **Everyone** (the whole company), one **department room** per department (a person sees the rooms for the departments their role can open, same rule as the top menu: `departmentsFor`), and **private messages** between two people (room key `dm:<idA>:<idB>`, ids sorted; nobody else can read them, not even the Owner). Everything the server does re-checks that the person may use the room. **Live** means the open chat asks `/api/chat/poll` every 2.5 seconds (Vercel can't hold a permanent connection) for messages created, edited or deleted since its cursor (`changed_at`), plus who is online and the unread counts; the top bar asks `/api/chat/summary` every 8 seconds on other pages; neither runs in a hidden tab. A paid real-time service could replace the polling later without changing the screens. **Unread** = messages from other people newer than the person's read mark for that room (`chat_reads`, only moves forward); a visible open room is marked read by the poll. New messages while the person is on another page give a red count, a pop-up with the sender and text, a soft chime (switchable, kept per browser) and "(n)" in the tab title. **Status**: Online, Busy, At lunch, Away, Out of office, plus a 60-character note. "Online" only counts while the person has been seen in the app within 90 seconds (every chat poll stamps `last_seen_at`, rewritten at most every 20 seconds); the other statuses are what the person chose, kept and shown dimmed when they have left. **Messages**: up to 2,000 characters, plain text only (web addresses become safe links, markup is never interpreted), emoji picker with search and recents (or the person's own keyboard), Enter sends and Shift+Enter makes a new line, edit and delete your own (the row stays so the conversation reads in order, with the text and any file removed); Admin and the Owner can also delete anyone's message in group rooms, never in private messages. More than 12 messages in 10 seconds from one person is slowed down. **Files and photos**: one per message, PNG/JPG/GIF/WebP/PDF/text/CSV/Word/Excel up to 4 MB, checked by their real contents, stored in the same private file store as Receiving photos (`chat/<company>/...`) and opened only through `/api/chat/files/<id>` by someone who may read that room; until the file store is connected, chat works and sending a file says so plainly. Not built yet: reactions, @mentions, group chats of your own choosing, search inside messages, message retention limits, push notifications when the browser is closed, and cleaning chat files out of the store when a closed company is purged (the rows go, as for every other table).
