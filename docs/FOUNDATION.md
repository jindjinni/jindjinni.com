# Foundation v1 — the benchmark for this system

Set on 2026-10-06 by Radcliffe Green (Plantarz Property Solutions LLC). This is the baseline the platform is built on.
Everything we add or change from here is measured against it. It is tagged in git as `foundation-v1`.

To see exactly what the foundation was at any time: `git show foundation-v1`.
To compare today's code with it: `git diff foundation-v1`.
To go back to it if something breaks badly: `git checkout foundation-v1` (or branch from it).

## What the foundation includes

**Platform**
- Multi-tenant: every company has its own login and data. Every table is scoped by `organizationId`; all server code gets the company from `src/lib/tenant.ts` (`requireOrg`), never from the browser.
- Roles in one file, `src/lib/permissions.ts`: owner, admin, purchasing manager, purchasing agent, receiver, accountant (and legacy staff). No scattered role checks.
- Sign-up with email verification, invitations, team management, Admin panel, company close/purge, data export, appearance (themes), terms acceptance, business profile.
- Hosting and services: GitHub, Vercel (with Blob storage and a nightly purge cron), Turso (libSQL), Next.js App Router, Drizzle, Auth.js, Shippo (labels), pdf-lib (PDFs). Resend email and the Anthropic label reader are optional.

**Purchasing department**
- Products catalog, categories, conditions, expiration ranges, per-product multipliers, bonus tiers, customers (with duplicate checks), archive, audit log.
- Quotations with the automatic price: Standard price x Expiry % x Condition %, rounded to cents. Price is editable by managers only; any manual price is clearly marked (`src/lib/purchasing-price.ts`; the server recalculates on save).
- Quotation import from spreadsheet, shipping labels, receipt PDF with its own layout.

**Receiving department** (the most critical module: no counterfeit or recalled items get through)
- Seven-step intake of each shipment, with photos, checks and the received-items board.
- Step 6 Lot & serial numbers: typed lists or clear group photos read in the browser (barcodes + text), the receiver confirms every number, the server then checks repeats, made-up or wrong-shaped serials, expiry and recall lists. Photo reading only ever suggests; it never decides.
- Recall lists and automatic recall checks; near-match warnings.
- Step 7 Adjustments: "Adjustment Quotation" shows right inside the adjustment screen with the reason, and refreshes itself after save, regenerate and finalize.
- Test-lock so test shipments cannot mix with real ones.

## The standards we keep (the "style" of the system)

1. **Plain language for people.** Screens, messages and PDFs say what happened and what to do next. No internal terms.
2. **Automatic first, manual by permission.** The system works out the answer (price, reason, checks); a person may adjust it only when their role allows, and an adjustment is visible as such.
3. **The server decides.** Anything the screen shows early (live price, photo-read numbers) is re-checked and recalculated on the server before it is saved.
4. **Safety over speed in Receiving.** A suspicious number, a repeat, or a recall hit stops or flags the item. A clean result never claims to prove authenticity ("OK" is not proof), and the receiver confirms what the reader suggested.
5. **Documents populate where you are working.** Finished quotations and adjustments appear in the same screen, simple format, with the reason; no extra windows or steps.
6. **One place for each rule.** Permissions in `permissions.ts`, pricing in `purchasing-price.ts`, number lists in `receiving-number-list.ts`, scan checks in `receiving-scan-core.ts`. Change the rule there, not in screens.
7. **Every change leaves a trail.** Receiving and Purchasing actions write to the audit log; money is never silently altered; voids reverse instead of delete.
8. **Tested before shipping.** Logic suites for numbers, scans, recalls, stress, and test-lock; browser end-to-end checks for the screens we change; `tsc` and `eslint` clean before a commit.
9. **Small, named commits.** One feature per commit, with a plain-language message.
10. **Every department has the same sidebar, and the company can edit it.** Each department (Purchasing, Receiving, and every one we add: Accounts, Customer Service, Inventory, Sales) opens with a colored sidebar down the left showing the company name and that department's tabs, with Setup pages under their own heading. An Administrator or Master Admin can press "Edit menu" at the bottom of the sidebar to rename any tab (and the Setup heading) and move tabs up or down; it saves for the whole company and has a "put the original names and order back" button. It is one shared component, `src/components/department-sidebar.tsx`, driven by one list per department in `src/lib/sidebar-menu.ts` (`DEPARTMENT_MENUS`) and saved in `organizations.sidebar_menus`. **To add a department:** add its tabs to `DEPARTMENT_MENUS`, use `<DepartmentSidebar>` in its layout (copy `receiving/layout.tsx`), and add its color in `src/lib/theme.ts`. Renaming and ordering then work with no more code. Tab names only change the sidebar; page titles stay as built. Roles decide which tabs a person sees (see the Purchasing layout), never the saved menu.
11. **A clean look, always: group the data, closed until opened.** The direction for the whole platform: wherever a page holds a lot of data, group it under closed, expandable headings by what it naturally belongs to (brand, day, customer, status), with totals and any warning badge on the closed line; a search or filter opens them; summary first, detail on request. For Receiving specifically, brand is the grouping. Every Receiving record or database page (Daily Receiving, Received Items, the Lot & Serial Tracker, and any new one such as Inventory or the weekly trackers) is grouped under the product brand, one closed line per brand with its totals and any recall or "needs a look" badge, opening to the detail. A search or filter opens the groups. The grouping rule lives in `src/lib/receiving-brand.ts`.

## Known open items at the time of this foundation

(The later review, decisions and follow-ups are kept in `docs/OPEN-ITEMS.md`.)

- Built (first sketch): **Accounts Department** (`/dashboard/accounts`; the accountant, Admin and Owner only). *To Be Paid* shows every submitted order Receiving set to "Need to Be Paid" as a small card on the left (like the Receiving intake list), under closed day headings (the day received, oldest first). Opening a card shows the **complete Receiving Intake Form**, read-only, with **Step 10 highlighted** ("Accounts works here") at the bottom: the amount to pay (the adjusted total if Receiving set one), the receipt upload (the same `PAYMENT_CONFIRMATION` file Receiving's Step 10 uses) and the Mark as Paid button, which stamps the date and time and sets the Accounts Decision/Status to Paid (one record: Receiving's own Step 10 shows the same thing). The accountant pays on a separate payables system, by ACH only, so there is no payment-method field. *Paid Orders* is the database of everything paid, built the same way: small cards on the left under closed headings for the day each was paid (the viewer's own day, newest first, Today marked, with totals), search and a paid-date range; opening a card shows the same complete form with a **PAID stamp** (date, time, amount) and the receipt in Step 10, so a Customer Service agent asked "did you pay me, and when?" can find the day or the name and see everything. There is also a CSV download. *Monthly Report* (`accounts/report`) is the report pulled at the end of the day or month: one month at a time (month picker, previous/next), laid out like the old Airtable "Accounting Paid Orders" view: customer, date paid, final payout (the adjusted total when Receiving set one), and the items quoted for the order, newest first, with the month's total and a "View quotation" link per row. It never shows the quotation number. It prints / saves as PDF and downloads as CSV; months follow the viewer's own calendar. Code: `src/app/(dashboard)/dashboard/accounts/`, the shared form loader `receiving/intake/[id]/intake-loader.tsx` (`<IntakeFormFor focus="accounts">`), `src/lib/accounts-queries.ts`, `src/lib/accounts-rules.ts`, `src/app/actions/accounts.ts` (`markOrderPaid`). Marking Paid here does NOT email the customer; that is Customer Service's job and it uses the stored receipt.
- Built: **Customer Service Department** (`/dashboard/customer-service`; the new Customer Service role, Admin and Owner; no access to Purchasing, Receiving or Accounts, but it can open receiving photos and adjustment PDFs). This is the **only** place a customer is emailed about payment, by **email only** (no texting), and **nothing is sent automatically**: *To Be Emailed* lists every submitted order Accounts marked Paid that has not been emailed, under closed day headings (the day paid, longest wait first) with totals, search, an "Only ready to send" filter and a Ready / Needs attention badge. Opening one (`customer-service/order/[id]`) shows the payment (paid date/time, ACH direct deposit, amount, receipt link), the exact email the customer will get (template picked by `pickEmailTemplate`: Standard, Packaging notice, Adjustment, Adjustment + packaging; rendered in a sandboxed preview), the attachments (payment receipt, revised invoice / adjusted quotation PDF, note-for-customer and inspection photos), and one **editable field, the note to the customer**; the approved wording stays fixed. Send is off until `emailReadiness` (`src/lib/customer-service-rules.ts`) has no blockers (emails on, submitted, Paid, valid address, receipt attached, and for adjustments a note, the adjusted payout and the revised invoice); the server re-checks. A separate manual *Send a packaging warning* is offered when the package was Not Acceptable. Every send writes a row in `receiving_customer_emails` (exact subject and body, attachment names, files left off, hidden copies, who and when); *Emailed* lists them under the day sent, newest first, and each order shows its full history with the exact email; *Resend* asks for confirmation and adds another log row. *Email Settings* (Setup, admin only) holds the on/off switch, sender name, reply-to, hidden copies, the **website link** (required: every email tells customers where to submit new orders, so Send is blocked without it) and the packaging-guide link (moved here from Receiving; the old Receiving address forwards). Below them are the **email templates** (Standard, Packaging notice, Adjustment, Adjustment + packaging, Packaging warning): closed headings that open into an editor (subject, text with `{placeholders}`, a live preview with sample details, Save, and "put the original wording back"). The original approved wording lives in `src/lib/email-templates.ts`; a company's edits are stored in `receiving_email_templates`. Saving checks the same rules the editor shows: only known placeholders, and every payment email keeps `{finalAmount}`, a place for the agent's note (`{note}` or `{adjustmentDetails}`) and `{website}`. Which template an order gets is automatic from Receiving's answers (`pickEmailTemplate`: Adjustment needed = Yes picks an adjustment template; packaging Not Acceptable picks the packaging version; otherwise Standard). The agent's note and the receipt, revised invoice and photos attached in Receiving/Accounts are added automatically and are not part of the wording. Code: `customer-service/`, `src/lib/customer-service-queries.ts`, `src/app/actions/customer-service.ts`, `planCustomerEmail` / `deliverCustomerEmail` in `src/lib/receiving-service.ts`. Receiving no longer sends anything; its Step 10 only shows when Customer Service emailed the customer. Customers only receive mail once the sending domain is verified in Resend (`RESEND_FROM_EMAIL`). **Email connector** (Email Settings, top card, admin only): a company can link the mailbox it already uses for payables (including one on its own domain, e.g. payables@theircompany.com) so customer emails come from that address instead of the platform's. Three ways, all in `src/lib/email-connector.ts`: *Google* (Gmail / Google Workspace, one click, permission to send only, `gmail.send`), *Microsoft* (Outlook / Microsoft 365, one click, `Mail.Send`; sent through a Graph draft so attachments of any size work), and *Any other email* (address + password / app password over SMTP, `src/lib/email-smtp.ts`; the form works out the mail host from the address, sends Google/Microsoft addresses to the one-click buttons, and tests the login before saving). One connection per company (`email_connections`); the permission token or password is stored encrypted (AES-256-GCM, key from `EMAIL_TOKEN_KEY` or derived from `AUTH_SECRET`) and never shown. The OAuth start/callback routes (`/api/email-connect/[provider]/start|callback`) are admin-only and use a signed, single-use state tied to the company, person and browser. `sendOrgEmail` is the one sending door: with a connection it sends from that mailbox, with none it uses Resend. If the mailbox's permission is revoked or the password changes, the connection becomes *Needs reconnect*, sending is blocked with a plain message (it never silently falls back to the platform address, so replies and sender reputation stay the company's), and an admin reconnects in one click. Each log row records the address it was sent from (`receiving_customer_emails.sent_from`). SMTP only allows ports 465/587/2525 and refuses private/internal hosts. Platform setup is in the environment: `GOOGLE_CLIENT_ID/SECRET` and `MICROSOFT_CLIENT_ID/SECRET` (a provider whose keys are missing shows as 'not set up yet' instead of a button).

## How to change the foundation

The foundation is a starting line, not a freeze. When we deliberately improve it, we tag the new state (`foundation-v2`, ...) and add a short note here saying what changed and why. Ordinary work does not need a new tag.
